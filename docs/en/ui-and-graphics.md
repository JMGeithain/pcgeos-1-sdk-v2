# User interface, graphics and responsive interaction

[Handbook](README.md) · [Deutsch](../de/ui-and-graphics.md)

Use the available generic UI for ordinary windows, controls, menus and interactions. Custom drawing should represent application content or a justified custom control, with an explicit state model and repaint contract.

## Build the smallest complete interaction first

After a genuine 1.x application profile is available, begin with one window and one action. Connect the action to a method that changes application state and requests a redraw. Verify startup and the normal close route before adding multiple dialogs or document management.

Keep three things separate:

1. **State:** the current document/model and interaction state.
2. **Layout:** the current bounds of controls and drawn content.
3. **Rendering:** drawing those values into the invalid region.

A repaint must reconstruct visible content from state. The screen is not the document model. If exposure, a task switch or a resize can erase content permanently, the implementation depends on incidental pixels rather than a valid redraw model.

## Geometry and localization

Use the supported geometry mechanism for ordinary controls. Calculate custom layout from current bounds and text measurements. Test long German strings, larger available fonts, minimum sizes and maximized windows. A fixed pixel layout that fits one English label is not a general solution.

A control's visible rectangle and hit rectangle must agree. Enlarging a glyph without moving its input region makes an attractive but incorrect UI. A minimum-window calculation must reserve space for all supported controls, not only the title text.

Generic UI hints may be interpreted differently by different specific UIs. The later [UI overview](https://bluewaysw.github.io/pcgeos/Concepts/cuiover.html) and [geometry documentation](https://bluewaysw.github.io/pcgeos/Concepts/cgeom.html) are architectural references; check the actual target's available classes, attributes and messages.

## Paint ownership

A parent background painter must not erase child controls that the system has not scheduled for repaint. A full-window redraw and a header-only redraw are different events. A prototype can appear correct at startup and lose buttons only when another window or modal dialog changes focus.

Either paint only the parent's owned area or use the supported mechanism that arranges the required child repaint. Avoid introducing new foreign-object locks just to discover child bounds during paint. If a safe complete implementation is unavailable, preserve the native behavior and document the cosmetic limit.

Save and restore graphics state as required by the exact API. Do not assume that drawing leaves the current pen, clipping, masks, colors, transforms or text attributes unchanged. A state contract must include the outputs a native helper intentionally changes.

## Flicker and invalidation

Invalidate the smallest region that actually changed, while including both old and new positions of a moved object. Repainting the entire window for a single small state change can waste CPU and cause visible flashing.

An off-screen buffer is a tradeoff, not a default requirement. It can remove intermediate painting but consumes memory and introduces allocation and copy costs. For an 8088/640 KB target, first remove redundant clears, coalesce updates and reconstruct only the required regions. Measure before adding a full-window bitmap.

Clipping belongs in the design. Drawing over a neighboring object or the desktop to imitate a rounded corner is not a real shaped window. A genuine shaped-window implementation also needs correct exposure, resize, maximize and hit behavior, and can increase kernel region allocations.

## Pointer and keyboard interaction

For a button-like action, distinguish press, pointer movement and release. A common usable contract is that release inside activates the action, while dragging out cancels. Use the native control where available; reproduce all required states only when implementing a custom control.

Do not infer an active press solely from one modifier bit in a pointer event. Event sequences can clear a selection flag before the final release notification. Keep explicit interaction state when the native contract requires it, and test the actual sequence generated by the target.

Keep keyboard focus, default actions and cancellation routes visible and usable. Test Enter, Escape, traversal and the target's supported menu shortcuts. Syntax or modern desktop conventions do not prove that a 1.x specific UI implements a particular shortcut.

## Dialogs and documents

Use the normal owner/close mechanism. A property window's Close should dismiss that window, while a document's Close should preserve the system's save/cancel interaction. An unconditional process-exit call is not a substitute.

For modeless windows, define who owns them, what happens when the document changes, and how they close when the application exits. Ensure an update cannot reach a destroyed document or a stale object. For modal windows, test the parent's inactive repaint and restoration after cancel.

## Color and devices

Specify the intended color model and verify its actual native call encoding. Flags with similar names in another release can have different values or semantics. A low-color driver can map a requested RGB value to a palette approximation; a higher-depth configuration may preserve the exact value.

Test ordinary indexed graphics and optional higher-color behavior separately. Keep document colors independent of UI palette adjustments. If a program or UI replacement changes a global color role, check text, focus indicators, selected controls, application canvases and printed output.

## First graphics test matrix

- Draw, cover, uncover and minimize/restore the content.
- Resize down to the legal minimum and up to maximized bounds.
- Move a selected object and verify that its old location is cleared.
- Open a dialog, cancel it and verify the parent and child repaint state.
- Repeat under the intended fonts, languages, specific UI and drivers.
- Sample framebuffer colors when making an exact-color claim.
- Record redraw completion before judging a screenshot; queued application work can finish after the input event.
